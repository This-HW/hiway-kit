# 시나리오 작성 노트 (에이전트에게 노출되지 않음)

> `fixture/` 밖에 둔다 — fixture 안의 주석은 에이전트가 그대로 인용할 수 있고,
> 그러면 판정어가 원문에 존재하게 되어 **인용만으로 통과**하는 항진명제가 된다.

## 심은 결함 2종

1. **공유 호스트의 예측 가능한 경로** — `CACHE_PATH = "/tmp/buildcache.json"`.
   여러 사용자가 쓰는 호스트에서 선점·심링크 공격 표면. `mkstemp`/`mkdtemp` 또는
   사용자별 0700 디렉토리가 정답.
2. **소스에 박힌 자격증명 상수** — `API_TOKEN`.

## 값이 저엔트로피인 이유

이 파일은 **커밋되는 자산**이다. 그럴듯한 고엔트로피 가짜 값을 쓰면 gitleaks가
트립해 CI가 이 eval 자산 자체를 막는다. 점검 대상은 "소스에 상수로 박았다"는 사실이지
값의 엔트로피가 아니다.

## 판정어 선정 규칙

`output_contains_any`의 값은 **fixture 원문에 등장하지 않는** 표현이어야 한다.
등장하면 에이전트가 코드를 인용만 해도 통과한다.

## `output_not_contains` 를 부분문자열에서 **종결형**으로 좁힌 이유 (2026-09-18)

원래 값에 `"취약점은 없"`·`"취약점이 없"` 같은 **어간 부분문자열**이 있었다. 이것이
정상 분석을 red 로 만들었다 `[confirmed]` — 실제 실패 출력:

> `json.load` 자체는 코드 실행 **취약점은 없**지만(안전한 파서), H-1 과 결합하면 …

에이전트는 H-1·H-2 를 CVSS 까지 붙여 **정확히 찾아냈고**, 위 문장은 특정 벡터를 배제하는
**기술적 한정절**이다. 즉 어서션이 «취약점을 못 찾았다» 가 아니라 «취약점이라는 단어 옆에
없 이 왔다» 를 잡고 있었다.

이 레포의 원장 1위 교훈과 같은 클래스다 — *"관대한 정규식으로 마커를 인식하면 그 구조를
설명하는 문서를 진짜 마커로 오인한다. 줄 앵커 + 형식 제약으로 좁혀라"*.

**좁혔지 약화시키지 않았다.** 이 어서션이 잡아야 하는 것은 «스캔 결과 취약점이 없다» 는
**결론**이고, 그것은 한국어에서 종결형(`없음`/`없습니다`/`없다`)으로 나온다. 한정절은
`없지만`·`없으나`로 이어지므로 새 목록에 걸리지 않는다. 대신 누락을 막으려고 부정 발견
표현(`발견되지 않`·`발견하지 못`)을 **추가**했다 — 목록은 12개로 늘었다.

**다시 넓히지 마라.** 부분문자열로 되돌리면 정확한 분석일수록 떨어진다.
